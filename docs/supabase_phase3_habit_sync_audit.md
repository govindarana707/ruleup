# Supabase Phase 3 habit sync audit

## Scope and verified architecture

Phase 3 covers `categories`, `habits`, `habit_options`, `habit_schedules`,
`point_rules`, `habit_pauses`, and `habit_reminders`. It deliberately excludes
check-ins, ledger entries, wallet calculations, rewards, reward images, and
redemptions.

The verified write path is unchanged:

`Flutter UI -> repository transaction -> Drift row + sync_queue row -> selected remote transport`

Repositories never wait for a network request. Their create, update,
archive/delete, validation, and queue insert happen locally. Synchronization is
started separately after auth restoration/login and from refresh/retry actions.
Queue rows are unique by `(user_id, entity_type, entity_id, operation)`, survive
process restarts, and reset their attempt counter when the same operation is
enqueued again.

## Entity inventory

All domain row classes (`Category`, `Habit`, `HabitOption`, `HabitSchedule`,
`PointRule`, `HabitPause`, and `HabitReminder`) are generated by Drift from the
table declarations. IDs are client-generated UUIDv4 values through
`createDatabaseUuid()` and are reused unchanged in D1 and PostgreSQL.

| Entity | Drift / D1 / PostgreSQL table | Repository and provider | Mutation semantics |
| --- | --- | --- | --- |
| Category | `categories` | `CategoryRepository` / `categoryRepositoryProvider` | Create/update locally; archive with `archived_at`; no hard delete. Ordered by `sort_order`, name, creation. |
| Habit | `habits` | `HabitRepository` / `habitRepositoryProvider` | Create/update locally; archive and restore; category is nullable. Measurement enum is `yes_no`, `duration`, `count`, or `value`. Missed-penalty configuration is non-positive. |
| Habit option | `habit_options` | `HabitOptionRepository` / `habitOptionRepositoryProvider` | Create/update; archive, not delete. Optional numeric value and stable sort order. Parent habit ownership is checked locally. |
| Habit schedule | `habit_schedules` | `HabitScheduleRepository` / `habitScheduleRepositoryProvider` | Create/update/hard-delete. JSON object configuration is validated against `daily`, `specific_days`, `times_per_week`, or `custom`. Mutations reschedule local notifications after persistence. |
| Point rule | `point_rules` | `PointRuleRepository` / `pointRuleRepositoryProvider` | Create/update/archive. Operators and nullable min/max shapes are validated. These rows are configuration only; no ledger mutation occurs. |
| Habit pause | `habit_pauses` | `HabitPauseRepository` / `habitPauseRepositoryProvider` | Create/update/hard-delete. Inclusive date-only ranges must be ordered and cannot overlap for one habit. Mutations reschedule local notifications. |
| Habit reminder | `habit_reminders` | `HabitReminderRepository` / `habitReminderRepositoryProvider` | At most one per user/habit; create/update/hard-delete. `time_of_day` is validated and stored as local wall-clock `HH:mm`; Supabase `time` values are normalized back to `HH:mm`. Notification scheduling stays on-device. |

Every repository query and mutation includes `user_id`. Child repositories also
verify that the parent habit belongs to that user. The presentation-level habit
management coordinator calls these repositories; it does not call a remote API.

## Legacy Worker and D1 behavior

Every entity pushes to `POST /sync/<entity_type>` and pulls through
`GET /sync/pull?cursor=<sequence>`. The Worker authenticates the legacy bearer
session, rejects client-supplied `userId`/`user_id`, derives ownership from the
session, validates UUIDs and fields, checks parent ownership, and performs a
stable-ID upsert. D1 compares incoming and stored ISO `updated_at` values; an
older/equal incoming mutation is treated as server-authoritative. Archive rows
remain present. Schedule, pause, and reminder deletes are hard deletes with
`sync_changes` tombstones.

D1 `sync_changes.sequence` is an autoincrement cursor scoped by authenticated
user. Pull pages contain 200 records and replay the current row snapshot; when a
snapshot has since been deleted, the event is returned as a tombstone. The
Flutter merger applies a page transactionally, refuses to overwrite an entity
with a pending local queue item, scopes IDs against other local users, upserts by
primary key, and advances the cursor only through applied records. Remote state
wins when no local mutation is pending.

Failures retain the queue row, increment attempts, record a bounded diagnostic,
and are retried by the explicit retry flow. Phase 3 adds permanent diagnostics
(`attempts = -1`) for ownership, integrity, validation/schema, and malformed
payload failures so they are not retried forever. A later local mutation resets
the item to pending. Network, auth/session expiry, foreign-key dependency, and
server failures remain retryable.

## Supabase mapping and transport

`HabitSyncMapper` is the single typed mapping boundary. It reads the generated
Drift model for the queued stable ID, produces PostgreSQL snake-case columns,
converts booleans and enums, decodes schedule JSON text into `jsonb`, preserves
date-only pause values, and serializes UTC timestamps. Pull mapping validates
types and ownership, converts `jsonb` back to local JSON text, and normalizes
PostgreSQL time values.

`SupabaseHabitSyncDataSourceImpl` uses the Phase 2 `SupabaseClient` session and
the anon/publishable key. It never uses the service-role key. Before every push
or pull it requires the queue/request owner to equal the authenticated Supabase
user. It sends stable-ID upserts and owner-scoped deletes. It reads only the
seven Phase 3 entity types from `sync_changes`, checks every returned owner, and
fetches each current row through RLS. Missing snapshots become replay-safe delete
tombstones.

The transport is scoped. In Supabase mode, out-of-scope queue rows (including
check-ins, ledger, and rewards) remain untouched rather than being sent to the
wrong backend. Supabase has its own durable cursor key,
`supabase_habit_pull_cursor`, so switching transports cannot confuse the D1 and
PostgreSQL sequence spaces. There are no dual writes and Realtime is not used.

Push order is deterministic: category, habit, option, schedule, point rule,
pause, reminder. Foreign-key failures remain queued and are retryable. Stable
primary keys make repeated upserts/deletes idempotent. The conflict model matches
the existing simple personal-data strategy: compare `updated_at`, ignore an
older/equal local snapshot, otherwise update the same UUID. Pull protects
pending local work and otherwise applies remote state. This is deterministic for
normal single-user devices but is not a CRDT.

## PostgreSQL and RLS review

The Phase 1 schema accurately represents the local/D1 UUIDs, booleans, enums,
nullable numeric fields, archive markers, sort order, date-only pauses, reminder
wall-clock time, and JSON schedule structure. PostgreSQL additionally enforces
ordered/non-overlapping pauses, point-rule shapes, and composite parent-owner
foreign keys.

Phase 3 adds `20260911000500_phase3_habit_sync_hardening.sql`. It changes the
shared timestamp trigger to retain an explicitly supplied offline mutation
timestamp (while still generating `now()` when an ordinary update does not
change it), adds an index for the user/entity/sequence pull pattern, and
reasserts forced RLS on the Phase 3 tables and change feed.

For each Phase 3 table, Phase 1 policies allow SELECT/INSERT/UPDATE/DELETE only
when `user_id = auth.uid()` (with both `USING` and `WITH CHECK` for updates).
Child composite foreign keys require `(parent_id, user_id)` to reference a
parent owned by the same user. `sync_changes` permits only owner-scoped SELECT;
clients have no insert/update/delete grant or policy. Trigger-generated events
run in the trusted definer function. No `USING (true)` or `WITH CHECK (true)`
policy exists for private data.

## Reminder and pause semantics

Pause dates are calendar dates, normalized as `YYYY-MM-DD`; they do not represent
instants and therefore do not shift between time zones. Both Drift logic and
PostgreSQL enforce inclusive non-overlap semantics.

Reminder time is intentionally a floating device-local wall-clock value. The
remote schema preserves that existing meaning with `time without time zone` and
does not claim Supabase sends notifications. The current model does not preserve
an IANA zone or per-reminder zone choice; adding cross-zone reminder intent is a
product decision for a later phase, not a migration-time behavior change.

## Later D1 data migration

A later bulk migration must insert users/auth identities first, then categories,
habits, options, schedules, point rules, pauses, and reminders in dependency
order. It must copy every existing `id`, `user_id`, timestamp, archive marker,
and child foreign key verbatim. Schedule JSON text must be parsed into `jsonb`;
D1 integer booleans must become PostgreSQL booleans; `HH:mm` reminder values and
date-only pause values must remain unchanged. It must not generate replacement
IDs or infer a different owner.

## Validation boundary

Hosted migration validation: **PASS**. Supabase CLI 2.117.0 was linked to an
authorized disposable hosted project. `npx supabase db push --dry-run` passed,
`npx supabase db push` applied all five Phase 1-3 migrations, and
`npx supabase migration list` confirmed that the five local versions exactly
match the hosted migration history.

Full Auth/JWT/RLS/Storage integration validation: **PENDING**. The hosted
migration result does not yet prove explicit UUID-preserving Auth Admin creation,
the `auth.users.id == profiles.id` trigger, synthetic `.invalid` email login,
real authenticated JWT CRUD, two-user cross-user RLS denial, authenticated
`sync_changes` runtime behavior, or Storage ownership/RLS behavior.

Mocked/local tests validate mapping, identity, scope, ordering, durable offline
queue behavior, independent cursors, pull merge/replay, and legacy transport
compatibility.
